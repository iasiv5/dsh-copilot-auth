# 数据级目录补丁，而非升级 pi-ai

DSH 0.1.2-rc.1 锁死 `@earendil-works/pi-ai@^0.84.2`（实际 0.84.4），其 github-copilot 目录是打包时硬编码的 JSON，过期后新模型（gemini-3.8-flash 等）无法加入、失效模型残留。升级 pi-ai 会与 DSH 版本产生断裂；目录外 id 在混合协议目录（3 种 wire 协议、无路由共享协议）下被 settings 写入校验直接拒绝，路由级 api 绕行会强制全路由单协议、破坏 Claude 系分派。因此我们决定：**插件在「手动刷新」时从 npm 拉取最新 pi-ai 的 `github-copilot.json`，与本机安装做数据级只增合并（按本机支持的协议白名单过滤），pi-ai 代码版本保持不变**。补丁被 DSH 升级冲掉后由插件下次启动自愈重打，不依赖 know-how 式人工维护。

## Considered Options

- 升级 DSH 内置 pi-ai：版本断裂，用户明确拒绝。
- 路由级 `api` 写入目录外 id：全路由强制单协议、丢失 filterModels 与多协议分派，淘汰。
- pnpm patch / 直改 node_modules 并记 know-how：升级即失效、需人工重建，且违背「不动 DSH 本体」的决策（改用插件自愈管理后此债消除）。
- 插件随版本携带静态目录覆盖层：保留为离线兜底；主路径是在线拉取，永远跟随最新目录。

## Consequences

- pi-ai 在模块加载时读目录 JSON，补丁写入后必须重启 dsh web 才生效 → 刷新是「打补丁 → 重启 → 插件补写 settings 目录」的两阶段流程；**同一 boot 内写过目录则禁止同步 settings**（内存目录仍是写前版本），由持久 journal 跨 boot 接力。
- **合并是只增不更新**：只补充本机从未见过的模型 id；上游对已有 id 的元数据修正不会同步。这是「永不覆盖」语义的代价，属有意取舍。
- **激活边界**：未激活实例的启动路径不触碰 pi-ai 安装树；自愈只重放历史上实际应用并验证过的补丁条目（durable applied entries），内置覆盖层仅是手动刷新时的离线数据源，不是自动应用的来源。
- 合并按协议白名单过滤，防御未来目录条目引用本机 pi-ai 不认识的协议。
- settings 目录的镜像重建（失效模型消失、定制被重置）只发生在用户经 diff 预览二次确认后；preview 与 apply 之间以输入 digest 绑定，任何输入漂移即 409 要求重新预览。不做备份功能——恢复地板为「补丁生效后原生从提供方获取可重建 账号可用∩可解析 集合」，不可恢复的仅是分钟级可重做的定制（2026-09-07 评审后按收窄表述重估，裁决维持）。
- **单进程单实例假设**：并发保护仅为宿主进程内 settled-tail mutex，不支持多实例并发刷新；settings 写入用 `expectedRevision` 真 CAS 防跨调用方竞态。
- **自愈兼容边界收窄**：自愈承诺仅覆盖「同 pi-ai 基线版本（0.84.4）被重装/覆盖后的恢复」；跨 pi-ai 版本时条目已原生存在则空操作，否则上报 `self-heal-incompatible`，不修改安装树。
