# 保守模型补充、显式重建与 profile 独立恢复

状态：2026-10-03 用户确认采纳，**尚未实现**。完整规则以[双 profile 设计规格](<../design/2026-10-03-dual-profile-auth-and-models.md>)为准；现行 v1.2.7 仍遵循历史实现。

旧“刷新”同时补充目录和重建用户模型列表，既让精简过的模型重新出现，又清除模型定制；共用用户级恢复文件还可能使一端确认的配置意图在另一端被消费。我们决定默认保留用户配置、让用户选择新增候选，另设明确的全量重建入口；刷新状态与恢复意图按稳定 profile 隔离，公共安装目录数据和宿主凭据库仍允许共享。该取舍增加预览、身份绑定、迁移和事务恢复的复杂度，换取可解释的操作后果与用户新修改优先。

## 保留与改变的边界

保留能力驱动的文件／注册表双通道、只增目录描述、不升级pi-ai、不创建额外提供方、不增加长期备份或自动重启。两个通道均须持久恢复意图、条件补偿、真实宿主列表验证；纯配置变更已被当前运行时验证时可立即生效，真正需要目录重新加载时才待重启。注册表“不写官方目录”不能被扩大为“不写任何用户数据”。

旧共享状态保留原件，不自动广播或消费配置意图；当前profile重新预览确认后才能采用历史条目。凭据共享意味着退出和重新授权有跨实例影响，本profile接受显式操作或观察到稳定凭据身份变化时，使旧待生效配置意图失效；它不要求删除非账号专属的公共目录条目。

## 用户后续裁决：软撤回与局部保证

用户确认D-01采用“请求撤回／结果待核实”，禁用无法保证安全的退出和新尝试切换；不再追求通过插件修复当前宿主的强取消／drain。用户随后明确选择范围A，替代“必须新增宿主持久授权边界”的方向：继续复用宿主现有认证和当前凭据事实，以本profile显式操作版本及观察到的稳定材料变化绑定本地缓存和意图，不承诺其他参与者停机期间同材料ABA的完整历史。

这个边界保留实用的账号变化保护，又避免为未经确认的强历史承诺引入宿主改造或全库协作协议。HMAC只作私有材料比较，不充当全局epoch；撤回未核实风险与AuthBinding是两条独立状态轴，绑定变化不能解除unsafe授权操作限制。原desktop已落地方案不是待重做的空白，仍是目录落地与快照恢复基础。实现详见设计§3，不在此复制协议。

## 考虑过的替代方案

- 继续用单一全量刷新：少一个入口，但名称与非破坏性期待冲突，明确淘汰。
- 自动识别被精简的模型：缺失本身无法证明排除意图，且历史基线迁移复杂；当前候选初始不选。
- 全面隔离账号与官方目录：需要另建认证体系或运行时目录覆盖能力，超出插件边界。
- 全部改为运行时注入：体验统一，但扩大对内部注册表的耦合；维持双通道。
- 仅改提示不改事务：无法解决伪退出、并发覆盖、丢失恢复意图与二次刷新失效，不足以达成目标。

## 与历史决策的关系

[ADR 0001](<0001-data-level-catalog-patch.md>)的目录只增、协议与供应链边界继续成立；单一镜像刷新与仅进程内互斥的产品边界由本决策取代。[ADR 0002](<0002-read-only-catalog-target-gate.md>)提供可写性分类的历史背景；[ADR 0003](<0003-catalog-registry-injection.md>)的注入通道继续保留，但“无写盘”“零破坏”“逐字节不变”等承诺必须限定到实际成功条件。历史记录不改写成新设计已上线，不涉及know-how热修退役。

实施分为[授权与状态](<../plans/2026-10-03-copilot-authorization-state-implementation-plan.md>)及[模型事务](<../plans/2026-10-03-copilot-model-transactions-implementation-plan.md>)两份计划，需评审后另行授权执行。


## 2026-10-05 追记（Q38）

真机验证裁决：移除「请求撤回」入口与 /cancel 路由——软撤回仅能撤销本地轮询（价值自限：15 分钟等待超时自然收敛），而其进程级风险锁存造成「登录成功却不能退出」死局。等待超时锁存与退出安全门保留；意图失效与晚写防护由 intentVersion＋删除后复核继续覆盖。以设计文档 §2 Q38 为准。
